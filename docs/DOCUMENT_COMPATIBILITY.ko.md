# 문서 호환성

[English](DOCUMENT_COMPATIBILITY.md)

## 제품의 약속

앞으로 Chemvas를 업데이트해도 현재 지원되는 정상적인 **v7 `.chemvas` 문서는
계속 열 수 있어야 하며**, 저장된 그림과 문서 정보를 편집 가능한 상태로 유지해야
합니다. 지원되는 그림을 복구하기 위해 이전 설치본을 따로 보관할 필요가 없어야
합니다. 이는 임시 마이그레이션 기간이 아니라 계속 지원하는 파일 계약입니다.

기준은 2026-09-13에 지원되는 v7 계약입니다. 선택적인 전하·라디칼 표시 색,
거울상 평형 화살표, 입체배치 미지정 교차 이중결합 `double_either`, 이미지, 그룹,
원근 좌표, Calculation Plan v2를 포함합니다. 선택 필드가 없는 기존 v7 파일도
계속 지원합니다. 일부 과거 Chemvas 릴리스는 이 기능들이 추가되기 전에도 같은
버전 번호를 썼기 때문에 모든 v7 표현을 읽지는 못합니다. 이 약속이 이미 설치된
과거 앱의 읽기 동작을 소급해서 바꾸지는 않습니다.

문서를 여는 것만으로 원본 파일을 다시 쓰지 않습니다. 사용자가 명시적으로 저장할
때는 현재 출력 형식을 사용하거나 표현을 정규화할 수 있지만, 지원되는 저장 정보를
보존해야 합니다. 이전 설치본과 파일을 공유할 때는 원본을 보관하거나 다른 이름으로
저장하는 것이 도움이 됩니다.

## 저장 형식 변경

- 앱 릴리스 번호와 문서 형식 번호는 별개입니다. 현재 쓰기 형식은 여전히 **v7**이며,
  이 정책 자체로 새 형식을 도입하지 않습니다.
- 기존 읽기 구현이 올바르게 해석하지 못하는 직렬화 변경에는 새 문서 형식 버전이
  필요합니다. 기존의 엄격한 스키마가 거부하는 새 필드, 새로운 열거 값, 필드 의미의
  변경도 포함합니다. 앞으로 호환되지 않는 기능을 v7 이름 아래 추가하지 않습니다.
  v8부터는 아래 "다음 형식 버전"의 개정 규칙이 그런 변경에 새 개정이 필요한지
  새 버전이 필요한지를 정하며, v7에서는 모두 새 버전이 필요합니다.
- 향후 쓰기 버전이 바뀌어도 읽기 지원 버전에서 v7을 제거하지 않습니다. 버전 해석은
  GUI·CLI 소비자마다 따로 구현하지 않고 문서 경계가 소유합니다. 실제 새 형식이
  도입될 때 필요한 변환을 그 경계에 구현하며, 미리 추측한 마이그레이션이나 기능
  협상 체계는 추가하지 않습니다.
- 형식 변경을 출시하기 전에 지원되는 과거 고정 예제를 열고, 편집·저장·재열기에서
  정보를 보존하는지 검증합니다. Graph Patch처럼 입력 버전을 유지하는 출력 경로도
  점검해야 합니다. 새 정보를 v7로 잘못 표시하거나 v7에 맞추기 위해 조용히 버리지
  않습니다.
- 알 수 없는 버전·필드, 잘못된 문서, 유효하지 않은 참조는 계속 오류입니다. 의미를
  추측하거나 미지원 정보를 조용히 빼거나 검증을 우회해서 정상적으로 열린 것처럼
  보이게 하지 않습니다.

## 다음 형식 버전

버전 7은 2026-09-13에 지원되는 계약으로 고정되며 개정 번호가 없고, 그 이름 아래
더 이상 아무것도 추가하지 않습니다. 그날 이전에는 v7 이름 아래 여러 기능이
추가됐기 때문에, 그중 하나보다 오래된 읽기 구현은 둘 다 `"version": 7`이라고
적혀 있어도 더 새로운 v7 파일을 잘못된 문서로 거부합니다. 파일이 어느 읽기
구현을 필요로 하는지 스스로 말하지 못합니다. 껍데기의 키 집합이 닫혀 있어 그
정보를 v7에 덧붙일 수도 없으므로, 이 정보는 다음 형식 버전과 함께 도입합니다.

다음 형식 버전 v8은 껍데기를 정확히 다음 키들로 확장합니다(릴리스 번호는
예시이며 실제 값은 쓰기 구현이 채웁니다).

```json
{
  "type": "chemvas",
  "version": 8,
  "schema": 1,
  "min_reader": "0.17.0",
  "state": {}
}
```

- `version`은 지금과 같은 형식 세대입니다. 읽기 약속의 단위이며, 한 세대를
  지원하는 읽기 구현은 자신이 아는 그 세대의 모든 개정을 읽고, 쓰기 버전이 바뀌어도
  지원하던 세대를 빼지 않습니다.
- `schema`는 세대 안의 개정 번호입니다. 1에서 시작해 **추가적** 변경마다 1씩
  올립니다. 추가적 변경이란 이전 개정에서 유효하던 모든 문서가 새 개정에서도 같은
  의미로 유효한 변경입니다. 새 선택 필드, 새 열거 값, 새 선택 컬렉션이 여기에
  해당하며, 오래된 개정의 엄격한 읽기 구현은 그런 문서를 여전히 거부합니다. 개정
  번호는 바로 그 거부를 설명합니다. **파괴적** 변경, 즉 필수 필드 추가, 의미 변경,
  필드 제거나 이름 변경, 껍데기 변경은 이전에 유효하던 어떤 문서가 더 이상 유효하지
  않거나 다른 뜻이 되는 변경이며, 새 세대가 필요하고 그때 개정 번호는 1로
  돌아갑니다. 기준은 기존 문서의 유효성과 의미이지, 오래된 읽기 구현이 새 문서를
  거부하는지가 아닙니다.
- `min_reader`는 이 개정을 온전히 읽는 가장 낮은 Chemvas 릴리스입니다. 쓰기
  구현이 `(version, schema)`를 키로 하는 코드 안의 표에서 채우며, 손으로 적지
  않습니다. 구현에는 표와 쓰기 구현의 일치를 유지하는 테스트가 있어야 합니다.

읽기 구현은 문서를 다음 순서로 판정하고 처음 실패한 항목을 보고합니다.

1. 모르는 `version`은 오늘의 메시지대로 거부하며, 이 릴리스가 읽는 세대들을
   밝힙니다.
2. 껍데기를 그 세대의 규칙으로, 개정과 무관하게 검증합니다. v7은 오늘처럼 정확히
   `type`, `version`, `state`, v8은 정확히 위의 키들이며 올바른 `type`, 1 이상의
   정수 `schema`, 릴리스 문자열인 `min_reader`, 객체인 `state`여야 합니다. 여기서
   실패한 문서는 더 새로운 문서가 아니라 잘못된 문서입니다.
3. 아는 `version`인데 `schema`가 이 릴리스가 아는 최고 개정보다 높으면 **잘못된
   문서가 아니라 더 새로운 문서**로 거부합니다. 메시지에는 문서의 형식과 개정, 이
   릴리스가 읽는 최고 개정, 그리고 `min_reader`에서 가져온 열 수 있는 릴리스를
   적습니다. 판정은 `schema`로만 하며 `min_reader`는 인용할 뿐 신뢰하지 않습니다.
4. 아는 개정은 오늘과 똑같이 엄격하게 검증합니다. 알 수 없는 필드, 알 수 없는
   열거 값, 유효하지 않은 참조는 계속 오류입니다. 개정 번호는 거부 이유를 설명할
   뿐 검증을 느슨하게 하지 않습니다.

`inspect-document`는 같은 세 값을 `document_format` 아래에 보고하게 되므로,
에이전트는 파일을 넘기기 전에 사용자가 설치한 릴리스와 비교할 수 있습니다.

v8 도입은 위 규칙을 따릅니다. v7 읽기를 유지하고, 문서 경계에서 변환하며, 고정된
v7 예제를 검증하고, v8 예제 집합을 따로 고정합니다. 문서를 실제로 바꿔야 해서 v8이
필요해지기 전까지는 아무것도 구현하지 않으며, 이 절은 그때 따를 요구사항입니다.

## 적용 범위와 한계

이 약속은 기본 문서 읽기와 편집 가능한 Chemvas SVG 안에 내장된 v7 문서에
적용됩니다. 클립보드 페이로드, CLI 요청·보고서, SVG 외부 메타데이터, 계산 전달
산출물에는 각자의 버전 계약이 있습니다. 기본 문서 형식이 바뀐다고 이 버전들이
자동으로 함께 바뀌지는 않습니다.

v7 이전 문서 지원을 추가하거나, 이전 앱이 새 형식으로 저장한 파일을 읽거나,
JSON 바이트가 같거나, 글꼴·플랫폼이 달라도 텍스트 픽셀이 같다는 보장은 아닙니다.
저장된 계산계획을 열 때 그 데이터는 보존하지만, 향후 화학 백엔드가 같은 결과를
재현하거나 미완성·오래된 계획이 실행 준비를 마쳤다는 뜻은 아닙니다. 과학적 검증과
문서 읽기 가능 여부는 별개입니다. 정확성·보안 수정에 따라 과거 구현이 실수로
허용했던 잘못된 입력은 계속 거부할 수 있습니다.

문서가 담은 계산 데이터는 선택적 RDKit 백엔드의 설치 여부와 관계없이 그림과 같은
조건으로 보존합니다. Chemvas는 계산할 수 없다는 이유로 계획을 버리지 않습니다.
Chemvas는 계획을 쓴 뒤 그림이 바뀌었는지를 기록하지 않습니다. 확인하는 것은
계획이 함께 저장되는 그림에 아직 맞는지이며, 기존의 세 지점이 그 결과를 알리되
어느 것도 스스로 데이터를 버리지 않습니다. 문서 검증은 더 이상 존재하지 않는
원자나 결합을 참조하는 계획을 거부하고, 데스크톱은 구성 성분·선언한 전하·대응
원자가 그림과 더 이상 맞지 않는 계획을 저장하기 전에 물어서 참조가 아직 유효하면
무효한 초안으로 보존하고 참조가 깨졌을 때만 사용자의 동의를 받아 파일에서
제외하며, `inspect-plan`은 단계마다 준비 여부를 보고합니다. 결합 차수 변경처럼
이 사실들을 그대로 두는 편집은 모든 검사를 통과하므로, 계획이 여전히 의도한
화학을 기술하는지는 사용자의 판단으로 남습니다. 데이터는 보존하되 재검토가
필요하다고 알려진 것을 알린다는 것이 문서가 담는 모든 확장 데이터의 규칙입니다.

## 회귀 검증 기준

[`tests/fixtures/document-v7`](../tests/fixtures/document-v7)에는 사용자 연구 자료가
아닌 고정 합성 예제가 있습니다. 이 파일들의 버전은 숫자 `7`로 고정하며, 형식이
바뀔 때 현재 쓰기 코드로 다시 생성해서는 안 됩니다. 이들은 대표적인 검증 예제이지
모든 유효한 v7 문서를 열거한 완전한 명세는 아니므로, 도메인 검증 테스트도 계속
필요합니다.

[`test_document_compatibility.py`](../tests/test_document_compatibility.py)는 기본
파일 입출력, 편집 가능한 SVG, CLI의 정보 보존을 검사합니다.
[`test_document_edit_roundtrip.py`](../tests/test_document_edit_roundtrip.py)는
데스크톱의 편집·저장·재열기 경로를 검사합니다. 둘 다 `make check`에 포함됩니다.
과거 미지원 버전 테스트는 현재 쓰기 버전보다 낮은 모든 버전을 거부 대상으로 삼지
않고, 버전 1~6을 명시합니다. 쓰기 버전 상수만 바뀌었다고 v7 읽기 기준이 깨져서는
안 됩니다.
